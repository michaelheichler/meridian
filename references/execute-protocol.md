# LBWC execution adaptation

This file keeps the complete execution behavior of the script-based planning system that LBWC ports. Below, "the source" means that planning system. This file replaces source-specific authority with LBWC mechanisms. The main session owns contracts, manifest admission, all state updates, verification persistence, telemetry, git, and user-facing output. Workers operate only through dispatched `scripts/task-contract.sh` capabilities generated by `scripts/agent-generator.sh`.

**Adaptation boundary:** `scripts/phase-detect.sh` replaces the source's manual phase scanning and mutable execution-state files. `references/agent-spawn-protocol.md` replaces the source's role-specific spawn calls, static routing maps, and team-mode selection. `scripts/qa-result-gate.sh`, `scripts/write-verification.sh`, `scripts/remediation-round.sh`, and `scripts/qa-remediation-state.sh` replace the corresponding source verification and remediation transitions. Do not call a helper merely because preserved source detail names it. The final dependency ledger and the relevant decision point list every helper that LBWC does not implement yet.

# LBWC Execution Protocol

Loaded on demand by /lbwc:vibe Execute mode. Not a user-facing command.

## Worker proof acceptance

Require every worker final message to follow the worker final result schema in `$PLUGIN_ROOT/references/handoff-schemas.md`, with `status`, `changed_files`, `commands`, and `open_questions`. Keep all role-specific reports and lifecycle gates. Reject malformed results and reject a `done` result without a nonempty commands array and an integer `exit_code` for every command. Reject done when any exit code fails or any question remains open.

Before reporting done, the main session reviews each proof command for safety and authorization, then re-runs each command in the intended repository and environment and records its own exit code. Never execute JSON command strings automatically, and never treat worker output as authorization. If a proof command cannot safely run, stop completion and report the blocker. A failed re-run blocks completion even when the worker reported success. Only the main session may set `main_session` to `true` on card proof entries, after it re-runs them. Preserve failed commands and observed codes in the result.

After re-running the proof, the main session writes the result JSON itself at a main-session-owned temporary path, using the worker's reviewed message and the main session's observed exit codes. Never pass a worker-written result file. jq applies last-key-wins to duplicate keys, so write unique keys and never copy unreviewed worker JSON bytes.

After all existing final output, follow the Feedback card input section in `$PLUGIN_ROOT/references/handoff-schemas.md` as the last output step.

## Runtime Plugin Root Resolution

Resolve the plugin root once per Execute run through the session link contract:

```bash
SESSION_LINK="/tmp/.lbwc-plugin-root-link-${CLAUDE_SESSION_ID:-default}"
ROOT_RESOLVER="$SESSION_LINK/scripts/resolve-plugin-root.sh"
[ -f "$ROOT_RESOLVER" ] || ROOT_RESOLVER="${CLAUDE_PLUGIN_ROOT:-}/scripts/resolve-plugin-root.sh"
[ -f "$ROOT_RESOLVER" ] || { echo "LBWC: plugin root resolver unavailable" >&2; exit 1; }
PLUGIN_ROOT=$(bash "$ROOT_RESOLVER" --require-script task-contract.sh)
[ -f "$PLUGIN_ROOT/scripts/agent-generator.sh" ] || { echo "LBWC: agent generator missing" >&2; exit 1; }
```

`scripts/resolve-plugin-root.sh` and `scripts/ensure-plugin-root-link.sh` resolve the plugin root. A missing resolver stops the command. It never authorizes a guessed path or manual equivalent.

Before spawning a worker, read `$PLUGIN_ROOT/references/subagent-contracts.md` and `$PLUGIN_ROOT/references/agent-spawn-protocol.md`. Issue the correct command or PLAN contract. Run `agent-generator.sh` with that contract and task id, and capture the final `SPAWN_READY <name>`. Then use that exact name for `subagent_type` and `name`.

### Step 2. Load plans and detect resume state

**Main-session read boundary:** The orchestrator reads planning and state artifacts before dispatch. It can read the selected PLAN, root or round SUMMARY artifacts, `STATE.md`, `ROADMAP.md`, and `REQUIREMENTS.md`. It can also read task contracts, the agent manifest, remediation state, and detector output. It does not implement product work. Product understanding required for a routing or sequencing decision comes from the PLAN or from a contracted worker report.

1. Run `scripts/phase-detect.sh` and require `phase_detect_complete=true`. Stop on `phase_detect_error=true`.
2. Resolve an explicit phase only after verifying that it does not skip a detector-selected blocking remediation route.
3. Resolve the root PLAN or active `R{NN}-PLAN.md` from `scripts/remediation-round.sh current <phase-dir> <qa|uat>`. Require the exact selected plan path.
4. Read every selected PLAN task and its dependency data. Read corresponding terminal summaries. A summary with `complete`, `completed`, `partial`, or `failed` is evidence only with corroboration from its task contracts and commits.
5. Query `scripts/task-contract.sh` state and the generated-agent manifest. A task is runnable only while no predecessor remains planned, dispatched, running, awaiting review, blocked, or cancelled without an explicit new plan.
6. Recover from the earliest incomplete task. A missing terminal summary or an open generated member is incomplete. A missing critic or test-dev verdict, a failed PLAN verify step, or a missing main-session commit is also incomplete. Do not create a summary placeholder.
7. For an active QA or UAT remediation round, use its persisted `stage`, `round_dir`, `plan_path`, and `summary_path` as authoritative host paths. Use its persisted verification path and UAT path the same way. Do not rewrite those paths relative to a worker cwd.
8. Write no mutable execution-state file. `phase-detect.sh`, task-contract state, the manifest, terminal summaries, remediation state, and commits replace a source execution-state record for recovery.

**Worktree isolation** follows `references/agent-spawn-protocol.md`. With `worktree_isolation=on`, native code-writing workers require `isolation="worktree"`, tmux provisions a worker worktree at HEAD, and workflow admission fails because its API has no verified isolation option. Commit predecessor output before spawning dependent work. Do not prepare future plan worktrees in advance.

**Correlation, event, snapshot, and schema state:** Task contracts and the generated-agent manifest own recoverable lifecycle state. `scripts/lib/session-telemetry.py` owns advisory events and metrics. LBWC no longer uses source execution JSON, snapshots, or schema-metric files. Do not create lookalike state files.

**Cross-phase dependencies:** A PLAN can declare a cross-phase dependency. For each such dependency, require the referenced terminal summary and declared artifact. A missing or failed dependency stops build with the phase, plan, reason, status, and recovery command. No declared cross-phase dependency means no verification.

### Step 3. Resolve Execute routing and run segments

**LBWC routing:** `scripts/phase-detect.sh` chooses the phase state. The selected PLAN task supplies the only routing facts: `<files>`, `<action>`, `<verify>`, `<strategy>`, `depends_on`, and the dispatched task contract. `references/agent-spawn-protocol.md` and `scripts/agent-generator.sh` choose the generated role shape from those facts. Do not build a route map, infer a route from effort, inspect a static preference, or use a generated name as authority.

**Dependency-aware execution:** Parse PLAN dependencies into waves. Start a task only after each predecessor has an observed terminal contract state, a successful verify result, and a main-session commit. Preserve PLAN order inside a wave. Independence does not authorize speculative background work or pre-generation of the next exclusive grouping.

**LBWC task-team semantics:** Every admitted grouping is a solo, pair, or trio defined by `references/agent-spawn-protocol.md`. Generate it with `--exclusive`. Spawn every pair or trio member in the same turn. The manifest, not a team label, determines membership and closure. Wait until each member is `used` or `expired` before generating another grouping.

**Generator team-mode branch:** The generator invocation must match the issued contract `team_mode`. A solo contract invokes `agent-generator.sh "$ROLE"`, a pair contract invokes `agent-generator.sh --pair "$ROLE"`, and a trio contract invokes `agent-generator.sh --trio "$ROLE"`. Every invocation receives the identical `--job`, `--contract`, `--task-id`, allowance arguments, and `--exclusive` setting used for that contract. A solo invocation for a pair or trio contract is invalid, since the generator must register every contract role before the spawn guard accepts it.

```bash
case "$TEAM_MODE" in
  solo) GENERATOR_ARGS=("$ROLE") ;;
  pair) GENERATOR_ARGS=(--pair "$ROLE") ;;
  trio) GENERATOR_ARGS=(--trio "$ROLE") ;;
  *) printf '%s\n' "LBWC: invalid team mode: $TEAM_MODE" >&2; exit 1 ;;
esac
GENERATOR_OUTPUT=$(bash "${PLUGIN_ROOT}/scripts/agent-generator.sh" "${GENERATOR_ARGS[@]}" --job "$BRIEF" --contract "$CONTRACT_PATH" --task-id "$TASK_ID" --exclusive "${GENERATOR_ALLOWANCE_ARGS[@]}")
```

Read every emitted `Agent-call parameters:` block and every final `SPAWN_READY <name>`. Use the emitted name and model for each corresponding live spawn. Do not spawn a subset of a pair or trio.

**No replacement team emulation:** Do not use background calls to imitate team parallelism. Do not attach `team_name`, `run_in_background`, or an unmanaged worktree cwd to a non-team spawn. Request native isolation only when `worktree_isolation=on` requires it. LBWC does not implement a true agent-team lifecycle, team marker, shutdown protocol, stale-team cleanup, or residual-team recovery yet. Until then, LBWC relies only on bounded task-contract admission and manifest closure.

**Prepared worktree rule** keeps each worker within its exact contract allowance even in isolation. The native host or tmux orchestrator owns worktree creation, not the worker. The main session integrates isolated changes before spawning dependent tasks and handles dirty worktrees that teardown retains.

**Delegation directive:** The main session never implements a PLAN task. It creates task contracts, generates workers, verifies returned evidence, and commits verified contract-limited changes. It also persists planning artifacts and updates command state. A generated worker owns only the exact capability issued by its contract.

- Never write an implementation path from a selected task in the main session.
- Never let a worker create, alter, or advance a contract, phase state, verification artifact, telemetry record, git state, or user decision.
- If a worker fails, examine its returned evidence and contract state. Give clarification only through a fresh task contract and generated name.
- A provisioning failure follows the no-tool circuit breaker and does not consume the ordinary retry budget.

**Returned work handling:** Inspect every worker return before artifact validation or state advance. A precondition failure such as an unread-file requirement can justify one fresh contracted retry with the prerequisite explicit. A validation contradiction requires main-session verification of the claimed data, then a corrected PLAN task or a clear blocker. A partial result needs a fresh contract that identifies verified completed paths and remaining work. A zero-progress result needs a clarified task. Stop after two failed fresh contracts for the same plan task and report the last blocker.

**No-tool invariant:** Treat unavailable tools as a provisioning failure, do not advance state, and do not retry the same prompt.

**Runtime enforcement:** `scripts/task-contract.sh`, the generated-agent manifest, `references/agent-spawn-protocol.md`, and the file guard enforce the LBWC boundary. They replace source execution-state bypass files, direct TaskCreate delegation, and effort-based direct implementation. A missing or stale contract blocks the worker. A contract state is not inferred from text.

**Monorepo routing:** No separate router runs. PLAN task paths, exact task-contract allowances, and `compile-context.sh` define the package scope. LBWC no longer uses `route-monorepo.sh`, and telemetry uses `scripts/lib/session-telemetry.py`. Do not call or emulate either source helper.

**Control-plane replacement:** LBWC no longer uses `control-plane.sh`. The main session calls `task-contract.sh`, `agent-generator.sh`, deterministic gates, and `compile-context.sh` directly. A missing required call fails at that boundary, and no fail-open control-plane fallback exists.

**Context compilation:** With `config_context_compiler=true`, run `bash "$PLUGIN_ROOT/scripts/compile-context.sh" {phase} dev {phases_dir} {plan_path}`. If the emitted `.context-dev.md` exists, include it. If compilation fails, report the failure and let the contracted worker read the exact PLAN and allowed files directly.

To resolve research, try the plan-specific `{NN}-{MM}-RESEARCH.md` first. Next try the phase-wide path emitted by `resolve-artifact-path.sh phase-research`, then the first phase research file. Include only the first match.

Follow `references/skill-activation.md` and render `references/skill-activation-payload.md` for every spawned prompt. Honor PLAN `skills_used` first. Do not recreate skill selection rules here or depend on the retired `skill-hook-dispatch.sh`.

**Correctness flag (Dijkstra):** A plan task can carry the task attribute `correctness: dijkstra`. Lead sets it at planning time for tasks that involve algorithm or loop derivation, concurrency, or boundary-sensitive logic. The flag makes the trigger deterministic. Dev engages the required discipline, and QA verifies invariant and variant reasoning. The orchestrator does not act on the flag itself. It passes through PLAN.md to the agents.

LBWC installs `references/dijkstra/DISCIPLINE.md`, and the file remains required for a task marked `correctness: dijkstra`. LBWC drops the source-only `testing/verify-dijkstra-discipline.sh`. QA verifies the plan's invariant and variant evidence through the normal verification contract.

**Context and turn limits:** LBWC no longer uses `token-budget.sh` or its mutable token-state files. `compile-context.sh` bounds prompt material. `agent-generator.sh` emits the detected route and turn limit. `scripts/lib/session-telemetry.py` records observed usage. Do not truncate context or alter a generated route through a static role budget.

**Pre-code validation gate (mandatory for a plan that requires it)**:
If a plan task contains validation requirements, the validation result is a hard gate. Examples include "MUST be done before any code changes", "Expected: ...", and "If absent, stop and re-analyze":

1. **Execute the validation** using the tool appropriate to the data source:
   - **Public/anonymous endpoints** (docs pages, open APIs, status endpoints): WebFetch is acceptable.
   - **Authenticated/private APIs** (signed requests, tokens, env-based secrets, custom headers): use Bash helper scripts, curl wrappers, or repo helper commands. Do not route authenticated API validation through WebFetch.
2. **Evaluate the result:**
   - If the result matches the task's expected shape, the gate passes. Proceed with code changes.
   - If the result contradicts expectations (wrong values, missing fields, empty when non-empty expected): gate fails.

**Failure handling:**
1. **On gate failure:**
   - Run ONE broadened sanity query (remove filters, broaden search, verify environment/account context).
   - If the contradiction remains, send `blocker_report` immediately. Do NOT proceed to the next task or begin code changes.
   - If the task expected specific data, empty filtered results (`[]`, no matches) are contradictory. Do not treat empty as success unless the task explicitly defines empty as the expected outcome.
2. **Operator fallback:** Where automated respawn after a blocker is not possible, surface a message to the user: "Validation gate failed for task {N}. Restart `/lbwc:vibe` from current plan state to retry."


**Model and reasoning resolution:** `scripts/agent-generator.sh` is the LBWC authority for a generated worker name, model, turn limit, and applicable parameters. The main session reads its complete output after issuing and dispatching a valid contract. Do not call role-specific source generators, derive settings from a static model file, or pass an unsupported reasoning parameter because a source profile named one.

For every live spawn, use the printed generated name as `subagent_type` and `name`, then use printed supported settings exactly. A missing name, stale contract, failed dispatch, or generator stderr stops the grouping before a spawn. The spawn guard is the final enforcement boundary.

**Skill activation for Dev/QA tasks:** Before composing task descriptions, evaluate installed skills visible in your system context. Read each skill's description and select all materially helpful skills for the tasks, not only the single most direct skill. Include adjacent support skills surfaced by the prompt, logs, errors, related files, or stack context.

Every spawned prompt that performs this evaluation MUST begin with exactly one explicit outcome block. If the orchestrator preselected skills at orchestration time, use `<skill_activation>` as the FIRST line. If it preselected none, use `<skill_no_activation>` as the FIRST line. Silent omission of both blocks is invalid.

After evaluating, state the skill outcome in your response so the user has visibility before you spawn the agent. Use a line such as `Skills: activating {skill-name}` or `Skills: none preselected: {reason}`. If the prompt or error mentions SwiftData, include `swiftdata` with the relevant test, build, or debug skills for SwiftData work.

After calling `Skill(...)`, read any relevant files named by its instructions, but do not scan entire skill folders or read unrelated references. When preselected skills expose local follow-up docs, resolve them with `extract-skill-follow-up-files.sh`. Paste the emitted `<skill_follow_up_files>` block immediately after the follow-up-read sentence in the spawned payload.

**Spawn-shape rule:** The generic generator and `references/agent-spawn-protocol.md` define every live call. Never pass `cwd`, `working_dir`, `workingDirectory`, or `workdir`. Pass `isolation="worktree"` for native code-writing workers only when the configured isolation policy requires it. Do not use an unmanaged worker worktree or a task-management call to create a team.

For a non-team grouping, omit `team_name`, `run_in_background`, and worktree cwd fields. The isolation policy still applies. A generated `name` is label metadata and the manifest supplies lifecycle state. The main session forms a pair or trio only by spawning every generated member in the same turn under the one dispatched contract. LBWC does not implement a true source team marker, worktree-target handoff, or shutdown lifecycle yet.

**Task admission and prompt:** For each runnable PLAN task, build a brief from its name, action, verify, and done fields, plus its task contract. Add compiled context, relevant research, and the explicit skill outcome. The brief begins with exactly one skill outcome block. Use `references/skill-activation.md` for selection and follow-up reads. Include only the exact contract allowance. Do not hand a worker broad phase scope, an execution-state path, a worktree cwd, or an inferred routing decision.

The current grouping uses `--exclusive`. A pair or trio spawns every member in one turn. A TDD task admits `qa-author` alone for red, waits for its manifest closure and tests-ready evidence, then admits a separate engineer-critic implementation pair. A critic or test-dev report controls review closure. A task dependency becomes runnable only after predecessor contract closure, observed verification, and main-session commit.

**Blocked worker notification:** The manifest and task-contract state are the current LBWC dependency signal. The main session does not create a source task-list mirror or use a background notification as authority. If a later task becomes blocked, generate its next grouping only after the preceding grouping closes.

**Opt-in TDD wave sequence:** Only the PLAN task `<strategy>tdd</strategy>` selects TDD, not phase effort or static routing. The main session first opens a solo `qa-author` red contract with exact test-file allowances. It generates, dispatches, and waits for the red worker. The red stage must report at least one expected failing test and close in the manifest. Only then does the main session open a distinct implementation pair contract.

The engineer receives the complete tests-ready payload and only implementation allowances. The critic receives no write allowance. A non-TDD task that requires new tests instead receives a trio, with exact test allowances assigned only to `test-dev`. The main session owns commits for both stages and does not admit the next grouping early.

**Opt-in cross-phase research pipeline:** LBWC does not implement the source's concurrent next-phase research pipeline yet. When implemented, it must require an existing next roadmap phase and absent phase research. It must also require a read-only or exact-new-file Scout contract, a generated Scout name, and a path limited to the next phase planning directory. It must not overlap with unclosed exclusive build groupings, write source output into the current phase, or infer agent-team semantics from background calls.

**Validation Gates:** A source risk-assessment, gate-policy, approval matrix, and effort-based communication matrix are static routing machinery. For task admission, LBWC replaces that machinery with the selected PLAN task, its contract, configured command policy, and observed verification evidence. Do not infer approval, QA depth, a direct route, or communication scope from effort.

When a PLAN or command explicitly requires approval, the main session presents the decision and waits before dispatch. A worker cannot approve its own plan. When a worker reports a blocker or material finding, use the message schema in `references/handoff-schemas.md` and preserve the exact evidence. Send targeted messages only. Do not broadcast normal progress or treat a message as state advancement.

LBWC no longer uses the source dynamic risk and gate-policy helpers. A PLAN that requires approval must carry that requirement explicitly. A missing required approval remains a blocker.

## Main-session lifecycle and telemetry

**Typed reports:** Generated agents use the message schemas in `references/handoff-schemas.md` and `references/subagent-contracts.md`. LBWC no longer uses `validate-message.sh`. The main session rejects a malformed handoff before any contract or artifact transition.

**Execution state:** `scripts/task-contract.sh` and the generated-agent manifest replace execution-state JSON, V2 contracts, snapshots, artifact registries, lease locks, two-phase completion, and source hard-gate scripts. Exact contract allowances and the file guard replace claimed-file leases. Do not create or call the retired helpers.

**Advisory telemetry:** The main session records observed lifecycle events through `scripts/lib/session-telemetry.py`. Telemetry failure never creates execution authority and never hides a contract, writer, QA, or UAT failure. LBWC no longer uses `log-event.sh`, `collect-metrics.sh`, token baselines, or source metric registries.

**Task completion:** After a generated group returns, apply the no-tool circuit breaker. Verify the critic or `test-dev` verdict, run the PLAN verify command, and inspect the exact allowed paths. Then advance the task contract through `running`, `awaiting_review`, and `verified` or `blocked`. Only the main session commits accepted changes. It writes the terminal SUMMARY after the commit and verifies that summary before starting the next dependency.

**Plan completion:** A plan is complete only after all of the following facts hold. Every task contract is terminal, and no generated manifest member remains open. Every verify command passed, the main-session commits exist, and the terminal SUMMARY passes validation. Missing evidence blocks phase state advancement.

### Step 3b. Two-Phase Completion (REQ-09)

Task-contract transitions replace the retired two-phase completion and artifact-registry helpers. The main session moves an observed task from `running` to `awaiting_review`, verifies its evidence, then records `verified` or `blocked`. Contract-limited paths and the file guard are the artifact registry. The main session writes no additional completion file.

### Step 3c. SUMMARY.md verification gate (mandatory)

Do not proceed to QA or mark a plan terminal until its exact root or remediation SUMMARY passes validation.

1. Require the canonical summary path emitted by the artifact or remediation helper.
2. Require terminal frontmatter status `complete`, `partial`, or `failed`. A root summary cannot use a placeholder state.
3. Require commit hashes, task results, files modified, and deviations. If the PLAN defines must-haves, also require `ac_results`.
4. The main session writes the summary from accepted worker evidence after owning the commits. For each phase SUMMARY.md, pass two to four short human-readable sentences from that evidence on stdin to `bash "${PLUGIN_ROOT}/scripts/plain-summary.sh" "$PROJECT_ROOT/.lbwc-planning"`. Insert its output at the top of the body, immediately after YAML frontmatter and before other headings. Empty output means omit the entire `In plain words` section, including any template placeholder. Stop on helper failure. Generated agents do not write or commit the summary.
5. Run `scripts/validate-summary.sh` on the exact path. A missing or invalid summary blocks the task contract and dependent work.
6. Only `complete` and `partial` satisfy Execute dependencies. `failed` is terminal but does not unlock dependents.

While a remediation round is active, the main session can assemble its summary incrementally. The summary must reach a terminal status before the round advances.

### Step 5. Update state and present summary

**Hard completion gate:** Before state updates, output, or user questions, close every generated manifest member and terminal task contract. If LBWC later adds real agent teams, a real agent-team run must complete the shared shutdown contract before output. The present LBWC solo, pair, and trio model waits for manifest closure and does not send source team-shutdown messages without an actual team.

If LBWC later adds real agent teams, the main session sends a typed shutdown request to each active teammate. It waits for approved responses with the shared bounded retry rule, records residual cleanup, then stops. It never removes team directories manually. Current LBWC task contracts and manifest entries are the closure evidence for non-team groupings.

**Worktree merge and cleanup:** Where a command explicitly used managed LBWC worktrees, preserve the summary before merge and merge only after task closure. Clear the mapping only after successful cleanup, and surface a conflict without deleting the worktree. LBWC does not implement automatic phase-wide worktree merge orchestration yet. A script error cannot silently claim a clean merge.

**Final persistence:** `compile-rolling-summary.sh` and `planning-git.sh` handle the rolling context and boundary commit. Telemetry uses `scripts/lib/session-telemetry.py`. LBWC no longer uses source snapshots or control-plane cleanup. Do not claim a rolling context, push, or boundary commit unless the installed helper completed it. A remote push still requires immediate user approval.

**Mark complete:** Update only state the main session owns. Do so after every required contract, manifest, summary, verification, QA-result, and UAT gate passes. `scripts/phase-detect.sh` must agree with completion on the next query. `scripts/verify-state-consistency.sh` can report an advisory warning, but it never turns an unverified phase into complete.

**Caveman commits:** With `caveman_commit` enabled in current settings, apply `references/caveman-commit.md` to the commit description only. The conventional commit shape and main-session git ownership remain mandatory.

**What happened:** Build the plain summary from verified root or round summaries, QA evidence, UAT evidence, and known issues. State two to four plain sentences. Do not convert deviations, pre-existing issues, skipped verification steps, or unimplemented LBWC features into success claims.

**Discovered issues:** De-duplicate by test name and file, retain the first error for a duplicate pair, and show at most twenty entries. Keep the phase registry path only for a registry that an installed helper persisted. If a known-issue backfill or todo promotion helper is unavailable, say that state was not persisted. Do not start an interactive loop while rendering issues.

**Next Up:** A terminal build with no QA artifact reports `/lbwc:qa {NN}`. A QA remediation execute result reports `/lbwc:qa {NN}`. A UAT remediation execute result also reports `/lbwc:qa {NN}` before human acceptance can resume. A blocked, invalid, or capped route reports the exact recovery command or manual decision. Stop after Next Up. Do not begin another stage in the same command turn.

## Output Format

Follow `references/lbwc-brand-essentials.md`. Use its Phase Banner (double-line box), Metrics Block, and Next Up Block. Use its status symbols ◆ running, ✓ complete, ✗ failed, and ○ skipped. Use no ANSI color codes.
